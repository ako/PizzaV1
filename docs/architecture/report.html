How the app's five modules depend on one another, where the bounded contexts really lie, which elements everything hangs on, and what to change. Every figure comes from mxcli report architecture and the mxcli catalog, read from the model itself; the generated demo-data seed is shown separately because it distorts the picture.

Module health

Fulfilment, Catalog and Core are close to self-contained (95–100 %). Shop's 60 % is a storefront's normal share: it reads the catalog and calls the order domain. Simulation is the outlier twice over — its cohesion is 2.8 % because the seed creates every catalog row and demo order from there, and still 9 % without it, because the simulator's job is to act on Fulfilment's orders.

Outside the app

Only the System module is used from the app modules (Shop → System (3), Simulation → System (3), Fulfilment → System (2), Core → System (1)): the guest user and session for carts, toasts and the session grant. No Marketplace module is called from app code; Atlas provides layouts, DataWidgets the data widgets.

Cycles

None between app modules, with or without navigation references. The module split (Simulation → Shop → Fulfilment → Catalog + Core) removed the one Fulfilment ↔ Shop cycle the single module had.

Recommendations

The simulator calls into the storefront in 5 places (Shop.SUB_Catalog_RecalculateAll, Shop.SUB_Line_ApplyDefaults, Shop.SUB_Line_Recalculate, Shop.SUB_Order_Place, Shop.SUB_Payment_Resolve): that is where the layering bends, and where the first two changes go.

  • Move the payment decision into Fulfilment. Shop.SUB_Payment_Resolve decides an attempt's outcome and performs T-02/T-03/T-04 on Fulfilment's order and attempt; the simulator calls it from above the storefront. In Fulfilment it sits next to SUB_Payment_Retry and the transitions, and Simulation no longer needs Shop for payments.
  • Give order placement and line pricing a home below the storefront. The traffic generator builds a Shop.CartLine and calls SUB_Line_ApplyDefaults, SUB_Line_Recalculate and SUB_Order_Place to create a simulated order the same way a guest does. That reuse is right — one pricing path — but it makes the simulator depend on the storefront's cart. A Fulfilment-level "place order from lines" with the pricing rules (BR-PRICE-02…04) lets both callers use it; the cart then only collects choices.
  • Keep the seed out of the architecture. 186 generated flows turn Simulation into a 2.8 %-cohesion module and fill the god-node list (SEED_Catalog with 837 outgoing references). Moving them to their own module (e.g. DemoData, layer 3) would leave Simulation's own 18 flows to be judged on their own and makes the next report readable without the "w/o seed" column.
  • Watch the two bridges. Shop.SUB_Line_Recalculate and Shop.SUB_Cart_Recalculate carry most shortest paths in the graph: configurator, cart, checkout and the traffic generator all run through them. They are also the open performance finding F6 (every line recalculated 2–4 times per add); changes there need the pricing tests (tests/pricing.test.mdl) and journeys J2, J9 and J11.
  • Treat Fulfilment.Order as a published contract. 223 flows in three modules read and write it directly. Additive changes are cheap; renaming or retyping an attribute is not.
  • Delete Shop.DS_Product_Recipe after re-anchoring requirement US-026 on Shop.SUB_Product_Recalculate.

How this was made

mxcli report architecture --format json (layers, cohesion, domain edges, communities, god nodes, bridges, hotspots, unused) and catalog queries for document counts and module edges without Simulation.SEED_*, in docs/architecture/arch.json (tools/collect.py); this page is rendered by tools/gen_arch.py. Cluster names, module roles, verdicts and recommendations are written by hand from that data.

Limits

References are counted from the model, not weighted by how often they run. Microflows reached only by URL, a JavaScript hook or a Java action count as unused. The "without seed" figures count catalog references by source module, which differs slightly from the report's own reference kinds.
