Summary

Two guest journeys (order a pizza, find a past order) on a volume seed of 400,000 orders (~10M rows, docs/perf/tools/seed.sql), 6 runs per step with run 0 as warm-up, before and after the fixes; pg_stat_statements and auto_explain on for the runs only (restored afterwards). This page is mxcli's built-in rendering: its server time counts every span in a step's window, including the simulator's 1.5 s background clock. The report with guest-only figures, findings and flame-chart pairs is docs/perf/report.html.

Journey steps

Median of the warm runs per step.

Database: volume seed: 400,000 guest orders over 365 days (1.0M lines, 3.2M log lines, 2.4M status changes), 150,000 abandoned carts, steady-state simulation events; seeded 2026-11-19

Changes made for the measurement (and restored afterwards):

  • pg_stat_statements and auto_explain on for the run (log_min_duration 20ms; restored afterwards)
  • 6 runs per step, run 0 warm-up
  • live poller on (2 s refresh is part of every step)

Background work ran during some steps — queued tasks, scheduled events, polling. It is not in their server or database time:

  • Guest orders a pizza / 1 open home: 1.1 ms
  • Guest orders a pizza / 3 open configurator: 1.3 ms
  • Guest orders a pizza / 8 place order and pay: 4683 ms

How this was measured

  • Each journey step is the time window its journey log record gives: from the action until its last /xas/ request answered and nothing new started for a short quiet period (the journey script decides). A step's work is the traces rooted in an HTTP request to the app (the port most requests go to) that starts inside the window — the whole trace, also where it outlasts the window. Other work that starts inside it — queued tasks, scheduled events, the task queue's polling — is background and is shown apart, not counted.
  • Browser time is the record's browserMs (or the window length). Server time is the union of the step's request roots — concurrent requests are not counted twice. Database time and query count are the database spans (db.system / db.statement) in those traces.
  • Each step ran several times; the first run warms caches and the JIT and is not counted. Figures are the median of the warm runs; the flame chart and statements are from the run closest to the median.
  • Plans come from Postgres auto_explain in JSON format (--plans <postgres log>), with the JIT block reported next to the plan.
  • Before/after compares against --baseline, an earlier performance report of the same journeys on the same seed.

What this does not cover

  • Results are only as representative as the seed: volume, distribution and dates. Seed dates relative to today — a seed dated from a fixed day made a "revertible" list about 120× too long and led to a wrong conclusion until checked.
  • A fair before/after needs the committed model as the "before", on the same seed: revert the change, restart and measure, rather than reuse an older run.
  • Access rules steer plans: an index on a status column can go unused because the access-rule subquery drives from an association, and a Mendix index cannot include an association. Such a finding needs a model change, not another index.
  • Spans show the runtime's work, not the browser's rendering; the difference between browser and server time is network and client.
  • Static N+1 candidates are shapes, not measurements: confirm each in a step's query count before changing it.
